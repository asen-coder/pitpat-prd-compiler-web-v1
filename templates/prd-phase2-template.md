# Phase 2 输出模板: prd-to-backend.md

## 模板结构

```markdown
# [Title] — 技术方案

## 1. 背景

当前的业务背景现状，简要说明以往业务所遇到的问题，给出本次项目迭代的原因，解决的技术痛点或业务痛点。

- 版本信息：[version]
- 需求信息：[prd filename 及链接]
- 相关PRD地址：[prd链接或文件路径]

## 2. 存储设计

MySQL表结构设计、ER图、ES存储设计等。说明Schema、字段类型、默认值、描述信息等。

### 2.1 DDL
[SQL statements，包含 pitpat 必需字段: id, is_delete, created_at, updated_at]

### 2.2 索引设计
[索引策略，基于查询模式分析]

### 2.3 数据迁移（如需要）
[迁移方案，是否需要停机，是否需要数据清洗]

## 3. 整体方案

- 流程图：[核心业务流程]
- 时序图：[关键场景的调用时序]
- 调用链路图：[服务间调用链路]

## 4. 接口定义

### 4.1 API详细设计
#### API-XXX: [路径]
- Controller: [service].controller.app.XxxController
- RequestDto: [字段定义，遵循 XxxRequestDto 命名]
- ResponseDto: [字段定义，遵循 XxxResponseDto 命名]
- QueryDto: [字段定义，遵循 XxxQueryDto 命名（如涉及查询）]
- Service方法: [遵循 Spring Data JPA 命名规范]
- 业务错误码: [可能的业务错误码及含义]

### 4.2 事件详细设计
#### EVENT-XXX: [事件名]
- Exchange: [名称, 类型: Topic/Direct/Fanout]
- Routing Key: [遵循 domain.event 格式]
- Queue: [队列名称]
- Consumer: [消费服务及处理逻辑]
- ACK策略: [手动确认/自动确认]
- 幂等保证: [如何保证消费幂等]

## 5. 关键技术

1. 是否需要**缓存**，如何设计（Redis Key 格式: module:method:params，必须设置过期时间）
2. 是否需要引入**设计模式**
3. 是否需要考虑**接口并发**（线程池、分布式锁）
4. 是否需要考虑**接口安全**（权限校验、数据脱敏）

## 6. 版本兼容方案

该版本上线后，是否有兼容性问题？

- 数据兼容：[新旧数据结构是否兼容，是否需要数据迁移]
- 接口兼容：[新增/修改/删除的接口，前端版本适配策略]
- 接口废弃：[需要废弃的旧接口及其替代方案]

## 7. 关联系统(功能)影响

在已有的业务上开发时，梳理清楚相关的设计背景：

- 整体方案设计：[关联系统的核心架构]
- 关键设计、表结构：[共享的表结构或接口]
- 性能瓶颈：[关联系统可能的性能影响]

> 如果不明确影响，应该主动找数据分析团队沟通。

## 8. 数据影响

- 是否有兼容方案，可以做到业务无感知
- 系统发布期间服务是否正常可用
- 系统发布期间对用户有没有影响
- 系统发布期间新老系统共存产生的数据有没有影响
- 各个系统发布顺序有没有要求

## 9. 上线后的步骤

1. 上线后是否需要数据清洗？什么时候执行，通过 TODO List 落地
2. 上线后的监控：对于核心业务、重要业务，关注上线后的接口响应、数据增长等指标
```

> 所有工程约定（DDL规范、Redis Key命名、API/Service/DTO命名、RabbitMQ规范）遵循 CLAUDE.md 中的定义，不在模板中重复。
