# Phase 2: Generate prd-to-backend.md — Implementation Mapping

This file contains the complete Phase 2 execution logic. Load this file when the user wants to generate `prd-to-backend.md` from an existing `prd.md`.

---

## Phase 2 Principles

1. **Project Context First:** MUST read `CLAUDE.md` before generating.
2. **Microservice Mapping:** Map every backend requirement to a specific pitpat module.
3. **Convention Compliance:** Apply pitpat engineering conventions.
4. **Task Dependency Ordering:** Decompose into phases (Phase 0: DB, Phase 1: Core, Phase 2: Integration).
5. **Risk Awareness:** Identify technical risks.
6. **Codebase-Aware Generation:** MUST scan actual codebase patterns before generating, not rely solely on `CLAUDE.md` static conventions. Use discovered patterns (table prefixes, Service method signatures, Redis/MQ/Lock key formats, Strategy patterns) to ensure new designs align with existing system.
7. **Architecture Risk Awareness:** MUST check generated design against known architecture constraints (God Classes, circular dependencies, layer violations, cross-domain coupling) and report risks with severity levels (BLOCK/WARN).

---

## Handoff Envelope Reading

Before scanning, read the handoff envelope from prd.md:

1. Search for `PRD-HANDOFF-ENVELOPE` marker in the generated prd.md
2. Extract `targetDomains` for targeted scan scope determination (Step 3.3)
3. Extract `domainObjects` for entity scan focus
4. Also read full prd.md for business context validation and architecture guardrail check (Step 5)

The envelope accelerates domain identification but does NOT replace full prd.md reading. If the envelope is missing (e.g., prd.md was generated by an older version), proceed with full prd.md parsing to extract BS-XXX and DO-XXX identifiers.

## Phase 2 Workflow

### Step 3: Collect Project Context

#### Step 3.1: Read CLAUDE.md

Read `CLAUDE.md` to extract:
- Microservice module structure and responsibilities
- Service ports and API prefix conventions
- Engineering conventions (Entity, DTO, Service naming, Redis, SQL, RabbitMQ)
- Technology stack and version constraints

#### Step 3.1b: Scan Cache Check

Before executing Steps 3.2-3.3, check for a valid scan cache:

1. Determine the prd directory (same directory as the input prd.md)
2. Check if `{prd-directory}/.prd-scan-cache.json` exists
3. If exists:
   - Read the cache file
   - Compare `gitSha` field with output of `git rev-parse HEAD`
   - If SHA matches → **cache hit**: skip Steps 3.2-3.3, use cached scan data for Step 4
   - If SHA mismatches → **cache stale**: proceed to Steps 3.2-3.3 (full scan)
4. If not exists → proceed to Steps 3.2-3.3 (full scan)

#### Step 3.2: Lightweight Full Scan

Use Glob and Grep tools to scan the entire codebase and collect structural metadata:

1. **Domain file distribution:** Scan `pitpat-data/` subdirectories, record file count per domain. Flag domains with >500 files as "bloated."
2. **God Class detection:** Use `wc -l` to measure line counts of all Manager and Service files. Flag classes exceeding thresholds: WARN >1000 lines, BLOCK >5000 lines.
3. **Package structure overview:** Scan `pitpat-api/` controller and manager packages to map module → package path relationships.
4. **Feign interface inventory:** Grep `@HttpExchange` annotations in `pitpat-feign/` to catalog all inter-service interfaces and their target services.
5. **MQ Consumer distribution:** Glob `pitpat-queue/**/consumer/` and `pitpat-queue/**/consumerv2/` to map domain → V1/V2 consumer counts. Flag domains with active V1→V2 migration.

#### Step 3.3: Deep Targeted Scan

Based on handoff envelope (or prd.md BS-XXX/DO-XXX analysis) — determine the target domain list. For each target domain, scan:

1. **Table prefix convention:** Grep `@TableName` annotations in the target domain's entity files. Extract the prefix pattern (e.g., `zns_`, `p_`, domain-specific). Use this pattern when generating DDL in Section 2.
2. **Redis key patterns:** Grep the target domain's sections in `RedisConstants.java` and related files. Extract key naming patterns, TTL ranges, and usage context. Use these patterns when designing cache in Section 5.
3. **Distributed lock patterns:** Grep the target domain's sections in `RedisLockConstants.java`. Extract lock key naming patterns and usage scenarios. Use these patterns when designing concurrency controls in Section 5.
4. **MQ event patterns:** Grep the target domain's sections in `QueueConstants.java` and `EventConstants.java`. Extract Exchange names, Queue names, Routing Key formats, and existing consumer classes. Use these patterns when designing events in Section 4.2.
5. **Strategy pattern detection:** Glob `**/strategy/` within the target domain. If strategy interfaces and implementations exist, note the pattern structure (interface name, factory class, concrete strategies). Recommend extending existing strategies when the PRD involves type-based dispatch.
6. **Service interface signatures:** Read the target domain's core Service interfaces to extract method naming style (e.g., `findXxx` vs `selectXxx`, `Page` vs `IPage`, parameter conventions). Match new Service method signatures to the domain's existing style.
7. **Manager cross-domain calls:** Read the target domain's Manager files to identify existing cross-domain communication patterns (which Feign interfaces are called, which Redis keys are shared, which MQ events are produced). Use these as reference when designing new cross-domain interactions.

#### Step 3.4: Write Scan Cache

After Steps 3.2-3.3 complete (full scan executed), write results to cache:

Write scan results to `{prd-directory}/.prd-scan-cache.json`:

```json
{
  "version": 1,
  "gitSha": "<output of git rev-parse HEAD>",
  "timestamp": "<ISO 8601 datetime>",
  "lightweightScan": {
    "domainFileDistribution": {},
    "godClassDetection": [],
    "packageStructure": {},
    "feignInterfaces": [],
    "mqConsumerDistribution": {}
  },
  "targetedScans": {
    "<domainName>": {
      "tablePrefix": "",
      "redisKeyPatterns": [],
      "lockPatterns": [],
      "mqEventPatterns": [],
      "strategyPatterns": [],
      "serviceSignatures": [],
      "managerCrossDomain": []
    }
  }
}
```

### Step 4: Generate prd-to-backend.md

**Load template on-demand:**
```
[Read templates/prd-phase2-template.md for complete template structure]
```

Follow the template format and write the file to disk.

**Silent quality boost — apply scan findings (or cached scan data) to template sections:**

| Template Section | How Scan Findings Improve Quality |
|----------------|-----------------------------------|
| §2 Storage Design (DDL) | Use scanned table prefix from Step 3.3.1 (not hardcoded `zns_`) |
| §4.1 API Design | Service method signatures match target domain's style from Step 3.3.6 |
| §4.2 Event Design | MQ Exchange/Queue/RoutingKey match existing constants from Step 3.3.4 |
| §5 Key Technologies | Cache/lock design references scanned Redis/Lock patterns from Step 3.3.2-3.3.3 |
| §7 Related System Impact | Populated from Feign interfaces (Step 3.2.4) and Manager cross-domain calls (Step 3.3.7) |
| §9 Post-Launch Steps | Consider Consumer version (V1/V2) implications from Step 3.2.5 |

### Step 5: Architecture Guardrail Check

After generating `prd-to-backend.md`, run the following checks against the output and the scan data from Step 3:

**BLOCK-level checks (must resolve):**

| # | Check | Threshold | Action |
|---|-------|-----------|--------|
| B1 | God Class new code | Target class >5000 lines | Recommend extracting to new BizService/Manager |
| B2 | Circular dependency | New bidirectional imports between activity ↔ user | Recommend Feign or domain event instead |
| B3 | Layer violation | Service layer calling other domain's Service | Recommend Manager orchestration or Feign |

**WARN-level checks (should address):**

| # | Check | Threshold | Action |
|---|-------|-----------|--------|
| W1 | God Class proximity | Target class >1000 lines | Suggest evaluating split |
| W2 | New cross-domain JOIN | Any new cross-domain SQL JOIN | Suggest application-layer assembly |
| W3 | Consumer version | Adding V1 consumer to domain with V2 consumers | Suggest V2 pattern |
| W4 | Redis key collision | Key pattern overlaps existing constants | Suggest key modification |

**Output format — append as Section 10 of `prd-to-backend.md`:**

```markdown
## 10. 架构风险清单

### BLOCK 级风险
- **RISK-001**: [BLOCK] 向 `XxxManager`（X行）添加新方法
  - 建议：提取为独立的 `XxxBizService` 或新 Manager

### WARN 级风险
- **RISK-002**: [WARN] 新增跨域调用 A → B
  - 当前耦合度：A→B X refs, B→A Y refs
  - 建议：确认是否可通过已有 Feign 接口实现
```

If no risks are found, output:
```markdown
## 10. 架构风险清单

> 本次技术方案未检测到架构风险。
```

3. **Microservice Accuracy:** Map to actual pitpat modules only.
4. **Convention Compliance:** All designs must follow pitpat engineering conventions from CLAUDE.md.
5. **Codebase Scan:** MUST perform Step 3.2 (lightweight full scan) and Step 3.3 (deep targeted scan) before generating, unless valid scan cache exists.
6. **Guardrail Output:** MUST append architecture risk checklist (Section 10) to the generated document after Step 5.
7. **Pattern Alignment:** All technical designs MUST align with patterns discovered in Step 3.3 (table prefixes, Service method signatures, Redis/MQ/Lock key formats, Strategy patterns), not generic conventions.
